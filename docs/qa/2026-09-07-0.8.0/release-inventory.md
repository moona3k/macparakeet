## Historical findings and disposition

### P1 documentation hazard — corrected in this QA branch

The original finding below applies to the baseline snapshot. `docs/human-qa-guide.md` now distinguishes the dev bundle identity from shared data paths and requires verified disposable state for destructive QA.

Location: `docs/human-qa-guide.md:43–47`; source `Sources/MacParakeetCore/Services/AppPaths.swift:13–26,86–118`; launcher `scripts/dev/run_app.sh:238–245`.

Trigger: follow the guide's advice to launch the dev app and test destructive flows believing it has a separate database because it has a separate bundle identifier.

Observed source: the normal app-support path is always `~/Library/Application Support/MacParakeet`. A bundle identifier does not change it. Only a DEBUG build with an explicitly supplied `MACPARAKEET_DEBUG_APP_STATE_DIR` changes the database/audio/model paths. Release builds ignore that variable. The launcher does not automatically create an isolated state root. Preferences also have mixed ownership: ordinary `.standard` settings use the current process domain, while `AppPaths.appDefaults()` opens the production named suite when the bundle ID differs. Keychain isolation is not implied by either mechanism.

Impact: a tester can delete or modify production recordings/vocabulary or affect shared settings while believing they are using disposable data. This is a concrete guide defect, not evidence that this QA run has damaged data.

Narrow fix: correct the guide; describe the separate TCC identity accurately and require test-owned fixtures/IDs or an explicitly isolated DEBUG state root for destructive checks. Explain the preference/Keychain limitation and that Release ignores the override. Do not add a new isolation architecture merely to repair the prose.

## Reuse notes

What worked for this inventory: start with the public tag and first-parent commits, then use changed paths to avoid counting feature-branch intermediate fixes multiple times. Read the tag's actual command list before declaring documented CLI capabilities new. Keep source evidence, historical checks, live executable proof and final signed distribution proof separate.

What did not suffice: the development release table alone overstates which CLI features are new; PR merge descriptions and green historical CI cannot establish current GUI/hardware behavior; a separate bundle identifier does not establish separate storage. The source inventory is intentionally not an exhaustive line-by-line audit of every changed function.

Append subsequent executed evidence in the parent QA log with exact candidate, command or interaction, fixture identity, expected/observed result, artifact paths, and known gaps. Do not turn pending cells into passes because related tests exist.
