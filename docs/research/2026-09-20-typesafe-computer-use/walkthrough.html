Jev, computer use, and what MacParakeet is proposing

Developer walkthrough · 2026-09-20 · companion to docs/research/2026-09-20-typesafe-computer-use/README.md

TL;DR
  • Jev is a chooser, not a doer. Code observes the screen, code writes the option list, Jev picks one option (with a probability per option), code executes and verifies. In both typesafe-computer-use and PR #1104, no LLM ever generates the options. They are built deterministically from the accessibility tree.
  • The two systems share the same loop (observe → options → Jev → act → verify). They differ in what surrounds the decision: how the screen is read, how the option list is shaped, how the result is verified, and how you debug it.
  • PR #1104 is stronger where it matters for a product: revocable authority, receipts, no-replay of uncertain effects, pay/delete/send confirmation, consent. Keep all of it.
  • typesafe-computer-use is stronger around the decision: a testable AX walk with off-screen controls, local OCR as a second source, a lean mutually-exclusive question set, and replay/timing/probability logging.
  • Proposal: no rewrite. Four transplants, in this order: (1) observability + replay, (2) pure AX walk, (3) leaner unconstrained request, (4) local OCR as a flagged secondary source. Six open questions at the end, each with a recommendation.

1. Jev in five minutes: your mental model, corrected

Your summary is right: one request carries state (any JSON: text, objects, arrays) and one or more questions. Each question has instructions (the judgment you want) and, for Choice and Score, criteria (the allowed answers, each with a description). Three primitives:

PrimitiveReturnsUse whenGotcha
Choicechoice, probabilities{option: p}, confidenceOne of a closed set. Up to 255 options.confidence is concentration of the distribution, not "probability the workflow is correct" and not permission to act.
Noulnoul (probability of yes)Does a condition hold?No separate confidence. 0.5 means "as likely yes as no", not "medium".
Scoreprobability-weighted position on ordered levelsDegree along a dimension; graded ranking with one Score per item.Levels must describe concrete situations.
Three corrections to the mental model that matter for computer use:
  1. Options come from code, not from an LLM. Both systems build the Choice criteria deterministically from the observed accessibility tree (button labels, field names, running apps). There is no generative step in front of the click. The moment you let a model invent the option list, you lose the guarantee that every option is something the host knows how to execute.
  2. Questions in one request are independent. They run in parallel over the same state and cannot read each other's answers. So you cannot say "if the operation is fill, which field?" as a dependent chain. You either (a) ask speculative questions with the premise stated in the instructions ("Assuming the next operation is fill, which field?") and let code consume only the applicable answer, or (b) make a second request. This one fact shapes both systems' payloads.
  3. Jev does not observe, plan, or verify. It never sees pixels or the live tree; it sees the text you send. It cannot simulate a multi-step transition. "Predict where the piece lands", not "play Tetris". And a Jev answer of finished is a judgment over the text you sent, not evidence the task succeeded.

Wire format (System One, as both systems call it)

// POST https://api.typesafe.ai/v1/systemone   Authorization: Bearer <key>
{
  "model": "jev-1.13.0",
  "state": { /* any JSON the questions may reference */ },
  "questions": {
    "<id>": { "type": "choice", "instructions": "…", "criteria": { "opt_a": "what a means", "opt_b": "…" } },
    "<id>": { "type": "noul",   "instructions": "Is X true?" },
    "<id>": { "type": "score",  "instructions": "…", "criteria": { "low": "…", "mid": "…", "high": "…" } }
  }
}

// 200 OK
{
  "model": "jev-1.13.0",
  "answers": {
    "<id>": { "type": "choice", "choice": "opt_a", "probabilities": { "opt_a": 0.81, "opt_b": 0.19 }, "confidence": 0.74 },
    "<id>": { "type": "noul",   "noul": 0.92 }
  }
}

Question ids are for your code; the model never sees them, so the instructions must carry the full meaning. Both projects validate the response strictly: every offered key present, probabilities sum ≈ 1, choice is the argmax, model string matches. Anything else executes nothing.

The design question for any computer-use system on Jev is therefore not "how smart is the model" but: how good is the observation, how well-shaped is the option list, how strict is the gate, and how honest is the verification. How code consumes the answers 
# decide.py
chosen = item.choice      # if kind == click_item
       | f"offscreen:{k}" # if kind == press_offscreen
       | kind.choice      # otherwise

confidence =
  min(kind.conf, item.conf)      # click names a target
  min(kind.conf, offscreen.conf) # press names a target
  kind.conf                      # else; a split on `site` never stops the run,
                                 # every page is recoverable
stop if kind in {done, none} or confidence < 0.4
Design principle stated in its README

"Every stall found while building this came from two options that meant the same thing. Confidence measures concentration, so overlapping options always read as doubt. Keep the action set mutually exclusive."

Also: only heads that name a target lower the gate confidence. If the outcome is recoverable (which website), a split does not stop the run.

What it does not have. No confirmation before "Buy". No receipt for a press (a click is a history line). No way to stop mid-action except Ctrl-C or slamming the mouse into the corner. A writer LLM composes field text from the goal and nearby screen text, proposes URLs for unknown sites, and reads the final screenshot to produce an answer. Great research harness; not a shippable safety model.

4. How PR #1104 asks Jev (three tiers)

Speech-first and native. Local STT gives a committed transcript. Then the router tries, in order, to avoid the model entirely.

Tier 1 — compile locally, no model. CODE
Exact grammar (type…, replace X with Y, click Save, press return, scroll down, undo), allowlisted sites (open gmail), running apps (switch to Slack), the Google Flights domain plan (fill origin/destination/date, unique city, Escape an overlay, press Search), web search boxes, unique Gmail Compose. If exactly one action compiles, execute it. Jev never sees these.
Tier 2 — several legal events, one outcome Choice. JEV
Code computes the VoiceControlSituation (plain / suggestionPicker / datePicker) and lists enabled events, each already bound to one executable action and a postcondition. When more than one is plausible, Jev picks among those ids only, plus insufficient_evidence and clarify. The option is phrased as a landing ("after the host acts, London, United Kingdom is the selected result"), not a keystroke. 
{
  "state": { "goal": "Find one-way flights from Zurich to London on September 20 2026.",
             "situation": "suggestionPicker", "kind": "outcome",
             "events": [ { "id": "n:14", "criteria": "After the host acts, London, United Kingdom is the selected result." },
                         { "id": "n:15", "criteria": "After the host acts, London, Ontario is the selected result." } ],
             "executed": ["setValue:n:3", "press:n:9"] },
  "questions": { "outcome": { "type": "choice",
      "instructions": "Choose which offered outcome should hold after the next host-compiled action…",
      "criteria": { "n:14": "…", "n:15": "…",
                    "insufficient_evidence": "None is a clear match. Do not guess.",
                    "clarify": "A required detail is missing." } } }
}
Gate: confidence ≥ 0.5, else clarify. The chosen event's pre-bound action executes; the next snapshot checks the postcondition (.selectedLabel).
Tier 3 — nothing compiles: unconstrained Jev over legality-filtered controls. JEV
Generic pages with no domain machine. Because questions are independent, the request asks every speculative branch at once: 
questions = {
  "operation":       Choice{ setValue | insertText | press | select | scroll | key | activateApp | finished | clarify }
  "target_press":    Choice{ every pressable target id + none }      // "Assuming the next operation is press…"
  "target_setValue": Choice{ every editable target id + none }
  "target_scroll":   Choice{ … }   // one head per operation present
  "value_n:3":       Choice{ up to 250 substrings of the utterance + none }  // one head PER editable target (≤24)
  "value_n:7":       Choice{ … }
  "consequence":     Choice{ ordinary | payment | destructive | externalCommitment | unknown }
  "direction":       Choice{ up | down }
  "key":             Choice{ return | escape | tab | none }   // Return omitted while a picker is open
}
Code reads operation, then target_<operation>, then value_<target> if filling. Each head gated at 0.5; consequence at 0.8. Payload capped at 120 KB or the turn fails with contextTooLarge.

4½. The real work: mapping the action space

Your guess is correct. Jev can only pick from options it is handed, and it can only pick well if every option (a) is something the host can execute in one step, (b) is distinct from every other option, and (c) is legal right now. So the bulk of the code in both systems is a compiler from screen facts to a closed, legal, executable option set. The Jev call is a few lines. Below is how MacParakeet does it, stage by stage.

① AX factsrole, label, frame, actions, settable, focused, value, enabled, secure

② Targetsone VoiceControlTarget per element, with the operations it supports
→
③ Situation + legalityfilter the set by what is legal right now
→
④ Enabled eventsbind (operation, target, value) → action + postcondition + criteria text
→
⑤ Choice criteriaevent id → landing sentence

① → ② Facts become targets with an operation set

The adapter walks the focused window (plus menu bar and focused element) and, for each node, derives which of seven operations it supports. This is the action space at the element level. Nothing here involves a model.

Result on the recorded Flights overlay snapshot: 73 targets. That is the raw action space for one observation: roughly 73 × |operations| candidate actions, most of them wrong.

② → ③ Situation and legality shrink the space

Code classifies the snapshot and removes options that are legal in general but wrong right now. This is where the recorded stalls were made impossible rather than unlikely.

enum VoiceControlSituation { plain, suggestionPicker, datePicker }   // recomputed from AX facts every snapshot

// suggestionPicker: a focused city row, or city rows + "Where else?" chrome
// datePicker:       any pressable target labelled "… departure date …"

VoiceControlLegality.offeredTargets(in: snapshot)
  .plain            → all page targets (never activateApp, never role=url — those are host-only)
  .suggestionPicker → only city rows + overlay chrome + the focused element (for Escape)
  .datePicker       → only calendar days + overlay chrome + the focused element

VoiceControlLegality.offeredKeys(in: snapshot)
  .plain                        → [return, escape, tab]
  .suggestionPicker/.datePicker → [escape]          // Return is NOT a landing while a picker is open
Why this matters for a classifier: if Return and "Search flights" are in the list while the overlay is up, Jev can pick them, and the recorded session shows it did. Removing them from the criteria is a stronger guarantee than any instruction text. Legality is the host's job, not the model's.

③ → ④ Domain machines turn goals into enabled events

For a goal the host understands (today: Google Flights, web search boxes, Gmail Compose, allowlisted sites, app activation, exact commands), code computes the next legal transitions as events. Each event is already bound to the exact action and, where possible, a postcondition to check on the next snapshot.

Roughly half the code exists to build and constrain the option set and to verify what happened after picking from it. The same is true of typesafe-computer-use: perception.py + macos.py + actions.py are ~70% of it; decide.py is 200 lines. This is the correct ratio for a System One design: the model is cheap and fast because the host did the work of making the question small and closed.

How the transplants fit this picture. Items 1–2 improve stage ① (more and better facts, testable) and the loop's feedback (replay). Item 3 improves stage ⑤ for the case where no domain machine exists (fewer, disjoint heads). Item 4 adds a second fact source to stage ①. None of them change the doctrine that stages ②–④ are host code.

6. What we propose to change

Keep the doctrine (code lists legal events; Jev chooses only when several are enabled; the host executes and verifies). Keep every safety mechanism. Transplant four subsystems, in this order.

Observability and replay first S
Record the full probability map per head and the offered keys in the local session log. Persist a redacted snapshot fixture per observation (ids, roles, labels, operations, focus; no values). Add macparakeet-cli voice-control replay <snapshot.json> --goal "…" that runs router + Jev and prints the compiled action or distribution without touching the screen. Add --dry-run ("would do: press 'Search flights' · actor local · route flight_plan"). Emit a per-turn timing line: observe 0.41s route 0.00s jev 0.24s execute 0.13s verify 0.36s.
Why first: every later change becomes measurable on saved snapshots instead of live Google Flights runs. The recorded overlay stall becomes a fixture.
Pure AX walk over an injectable source M
struct AXNodeFacts { role: String; label: String; frame: CGRect?; actions: Set<String> }
protocol AXTreeSource { func children(of: Node) -> [Node]; func facts(of: Node) -> AXNodeFacts }
struct AXTreeWalk { static func run(root, source, display, caps) -> (visible: [AXNode], offscreen: [AXNode], capped: Bool) }
Port TCU's eight pruning rules and their tests (off-display subtrees, < 4 pt slivers, closed AXMenu, nameless AXGroup, label inheritance from parent control / shallow AXStaticText, dedupe by role+label+frame, off-screen pressables collected separately, node/time caps reported). Read display bounds and the window frame once per observe, not per node. Read expensive attributes only for roles that use them. NativeVoiceControlAdapter.observe() becomes acquire → walk → TargetBuilder (our existing role/operation/secure/browser rules) → inject apps and destinations.
Payoff: the walk becomes unit-tested, faster, and gains off-screen controls ("click Note 900" without scrolling; AXPress does not need visibility).

Two outputs: (a) OCR-only blocks become role: "text" targets with an adapter-private pixel centre; a press posts a marked click and is received as unknown unless transition evidence changes; AX-first press always. Q2. Tier-3 value: one request with focused-only value, or always two requests when filling?

Independent questions force speculation. Per-target value heads are exact but explode payload; a second request adds ~250 ms only when filling an unfocused field.

Recommendation: one request with a value head only for the focused editable target (the common case after the router or a previous step focused it). If kind == fill and the target is not focused, one second request with a single value head. Never more than two round trips per step.
Q3. Do we adopt local OCR at all, given the "no OCR as primary grounder" stance?
Decided 2026-09-20 (owner): yes. On-device OCR is in, and not only as a way to find clickable text. It is a second source of state: prices, dates, counts, status lines, list contents and result rows that AX often omits, truncates, or exposes as unlabeled static text. Two roles, both local:
  1. Targets: OCR blocks with no AX match become role:"text" pressable targets with a pixel centre; AX-first press, pixel click only as fallback; received as unknown unless transition evidence changes.
  2. State: OCR text within the frontmost window feeds the snapshot summary (bounded, reading order, TCU's date hints applied) so Tier 2/3 Jev questions and local matchers see what the user sees, not only what the app declared.
Sequence: after the walk refactor (item 2) so the box-overlap merge has clean AX items. Behind a DEBUG flag first. ADR-033 amendment: "AX first; on-device Vision OCR may add text-only targets and window-scoped screen text to the observation; pixel click only as fallback; OCR text goes to Jev only under the existing cloud-context consent; no image is persisted or transmitted by default." Open sub-question moved to Q7.
Q7. How much OCR text goes on the Jev wire, and how is it redacted?

Follows from Q3. AX labels are already sent under consent; OCR widens that to everything visible in the window, including email bodies or document text the user did not mention.

Recommendation: same rule as AX today, tightened for volume: cap OCR-derived summary at the existing 4,000 chars, crop to the frontmost window, drop lines inside secure or excluded elements' frames, run the existing secure-label word filter over OCR lines, and never include OCR text in shareable diagnostics (local session log only, values-class). Consider a per-app opt-out list (password managers already excluded). Measure Jev latency and clarify rate with and without OCR state on the replay corpus before making it default-on.
Q4. Should Score appear anywhere in the loop?

Neither system uses Score for action selection; both use Choice over landings/items and TCU uses one Noul to verify a typed value.

Recommendation: not for action selection. Choice over enabled events is the right primitive because options are mutually exclusive landings. Score becomes useful later for ranking (e.g., "which of these five flight results best matches 'cheapest nonstop morning'") where one Score per item on a shared rubric is what the primitive is for. Keep it out of the click loop.
Q5. Persist redacted snapshot fixtures with control labels on disk?

Labels can be personal (email subjects, document titles). latest.json already stores labels locally; Copy diagnostics strips them.

Recommendation: yes, local-only, same folder and 20-session retention as the existing session log, values omitted, never referenced by the shareable copy. Add a "Delete Voice Control logs" action in the panel so the user controls the retention explicitly. Replay from a fixture needs labels; without them the fixture is useless for the stalls we actually hit.
Q6. Off-screen presses: allow the host to press a control the user cannot see?

TCU shows Notes rows, Dock items and scrolled-out links accept AXPress while invisible. It is powerful and slightly spooky.

Recommendation: allow only for explicitly named local commands ("click Note 900", "open Downloads in the Dock") where the user said the label, with receipts postcondition-only (the pressed element becomes focused/selected, or transition evidence changes). Do not offer off-screen controls to Tier-3 Jev initially. Revisit once the timing line shows how often "scroll to find it" is the stall.
