# Interactive meeting-split mockup

Historical task brief for the fictional HTML concept, not instructions for the app implementation. The user subsequently clarified that the optimal native UI/UX remains open to exploration and decision; the layout and controls below are not binding.

Goal: Produce a beautiful, self-contained HTML product mockup that lets a person split one saved MacParakeet recording into 2, 3, or 4 meetings and understand the consequences.

Context: This is an investigation of GitHub issue #895, not production code. Use synthetic sample content only. Main investigator is auditing data safety separately. Return the complete HTML in your final answer (no code fence); orchestrator saves it with apply_patch. Read only docs/brand-identity.md and spec/04-ui-patterns.md for visual context if useful. Do not explore the whole codebase.

Prototype-only design direction: Native macOS-inspired light window, system font (-apple-system), neutral white #ffffff, canvas #f5f5f7, sidebar #ececef, text #202124, muted #62646b, brand coral #E86B3B limited to meaningful actions. A meeting timeline with split markers is the main visual; quiet app chrome around it. No dark marketing page, oversized hero, gradients, emoji, external dependencies/fonts/images or network calls. Responsive at narrow widths, visible keyboard focus. A small top strip says 'Interactive concept · Issue #895' (use ordinary prose separators if preferred) and explicitly states all sample data and no files changed. Opening file directly must work.

Core interaction: saved recording 'Friday morning meetings', 1:48:00, date Sep 11, 2026, total 6480 seconds. Default no split boundaries. User opens More menu > Split recording... to enter editor (also prominent 'Try splitting this recording' outside app acceptable). Show transcript excerpts and timeline; clicking transcript boundary or entering mm:ss/hh:mm:ss and Add split adds a sorted unique cut. Use 36:20 (2180s), 1:12:10 (4330s), 1:30:00 (5400s) for sample meeting boundaries. Allow remove markers, change times, edit child titles; reject 00:00, total duration, duplicates and malformed timestamps visibly. Avoid creating zero-length parts. Model whole recording partition [0,cut1), ... [cutN,end], keep ALL audio, no break exclusion in first release. Display cut boundary confidence as 'Between transcript passages' for sample known safe gaps; arbitrary cuts during speech should visibly snap to a nearby safe passage boundary or reject with an explanation, never pretend arbitrary timing preserves sentence text.

Preview: list each resulting child title, original start/end, duration. Original kept explicitly. Notes, summaries and Ask history remain with original, children have their own transcript and audio; fresh summaries are optional later. Do not offer automatic AI analysis. Primary button 'Create N meetings' only enabled with cuts. Simulated progress with explicit 'Continue demo' button (no unsolicited animation), then success listing children plus accessible original. User can click each child to inspect its transcript with timestamps starting at zero. Success must expose source range and original link. Do not represent real audio playback: any transport should say preview position simulation or be absent. Put audible playback limitation in concept strip, not fake play behavior. Can allow 'Preview boundary' to show before/after transcript text.

Original retention / recovery: original unchanged and remains in Library; no delete original or generic undo that silently deletes children. A 'Reset demo' action resets memory only. On success offer open original, open each child, restart demo.

Scenario tabs below window: 'Two meetings', 'Four meetings', 'Audio removed', 'Transcript edited'. Each initializes relevant scenario and shows simple guided action buttons; no raw JSON. Audio-removed scenario allows text-only split only if timed transcript still valid, clearly 'Create N text-only meetings'. Edited transcript scenario blocks timed split with explanation that text changes do not have matching timestamps; offers safe cancel and conceptual regenerate timing step that requires explicit user action but do not actually perform ASR or erase edits. Better limit to explanation with original accessible. Current relevant state always visible in readable fields (parts, split points, original kept, audio availability).

Implementation: plain inline CSS and JS, no packages, no persistence. Keep state logic in small pure functions separate from DOM rendering, all visible actions functional. Use accessible semantic buttons/dialogs/labels. User input rendered with textContent or escaped. Close dialog/cancel returns to source with state unchanged. Include reasonable mobile layout. No prototype unit-test suite; orchestrator will browser-check flows and layout.
