# Storage and Audio Feasibility: Splitting One Saved Meeting Into 2–4 Meetings

## Current model (baseline: HEAD `1159dfca`)

A meeting is one `transcriptions` row (`sourceType == .meeting`) paired 1:1 with one session folder created at `startRecording()`: `AppPaths.meetingRecordingsDir/<sessionUUID>/` (`MeetingRecordingService.swift:611-612`). Nothing in the codebase models a meeting as a range into a shared parent; the folder *is* the meeting's storage unit, and `transcriptions.meetingArtifactFolderPath` is "the durable folder locator" while `filePath` is "only the mixed-audio playback/export path" (`spec/contracts/meeting-artifacts-v1.md:13-16`). `MeetingArtifactStore.sessionFolderURL(for:)` (`MeetingArtifactStore.swift:207-220`) resolves the folder from `meetingArtifactFolderPath` first, falling back to `filePath`'s parent directory — every artifact/audio/lock helper in the subsystem (`MeetingAudioFile`, `TranscriptionAssetCleanup`, `MeetingAudioRetentionSweeper`, recovery) goes through this same resolver or an equivalent alias check (`MeetingArtifactPathAliases.swift`), so folder identity is a single, well-factored seam.

Folder contents relevant to splitting (`spec/contracts/meeting-artifacts-v1.md:50-61`, `MeetingArtifactAudioFileNames.swift:3-11`):
- `microphone-raw.m4a`, `system-raw.m4a` — independent per-source captures, written by `MeetingAudioStorageWriter` (referenced in `MeetingAudioFile.swift:8`).
- `microphone-cleaned.m4a` — AEC-derived mic, produced once after stop.
- `meeting-playback.m4a` — the mixed/canonical file `transcriptions.filePath` points at, built once by `MeetingPlaybackArtifactBuilder` (`MeetingPlaybackArtifactBuilder.swift:57-117`) and never touched again.
- `meeting-recording-metadata.json` — `MeetingSourceAlignment` (per-source `startOffsetMs`, `writtenFrameCount`, `timelineFrameCount`, `sampleRate`) plus `MeetingCaptureReport` (`MeetingRecordingMetadata.swift:33-55`, `MeetingCaptureReport.swift:9-72`).
- `recording.lock` — presence alone is a hard retention-sweep and deletion barrier regardless of parseability (`spec/contracts/meeting-recovery-retention.md:183-201`). A saved/completed meeting normally has none; this only matters if split runs against a row still mid-finalization.
- Read-materialized artifacts (`manifest.json`, `meeting.md`, `transcript.json`, `notes.md`, `prompt-results*`) — all regenerated by `MeetingArtifactStore.materialize(transcription:promptResults:)` (`MeetingArtifactStore.swift:120-205`) from the DB row; never a source of truth.

**Timeline model.** `MeetingSourceAlignment.Track.startOffsetMs` anchors each source to a shared meeting-origin timeline (`MeetingRecordingMetadata.swift:24-30`); `writtenFrameCount` vs. optional `timelineFrameCount` distinguishes real captured frames from recovery-inserted silence padding (`MeetingRecordingMetadata.swift:9-13`). `MeetingCaptureReport.capturedDurationMs` is computed as `max(startOffsetMs + timelineDuration)` across selected sources (`MeetingCaptureReport.swift:135-139`), so both raw tracks and the mixed playback file already carry the offsets needed to convert a user-picked mm:ss cut point on `meeting-playback.m4a` into consistent sample offsets on `microphone-raw.m4a`/`system-raw.m4a`/`microphone-cleaned.m4a` — a genuine reusable seam, not something to invent.

**No existing range-extraction primitive.** I found no method that exports a sub-range of an `.m4a`. `MeetingPlaybackArtifactBuilder` only builds the *whole* playback file once; `MeetingRecordingRecoveryService.repairIfNeeded` (`MeetingRecordingRecoveryService.swift:650-686`) uses `AVAssetExportSession(asset:presetName: .appleM4A)` only to re-encode a fragmented file end-to-end for repair, not to trim it. Splitting will need new code, but the primitive is standard and low-risk: `AVAssetExportSession.timeRange` (a `CMTimeRange`) on the same `AVAssetExportPresetAppleM4A` preset already proven in the recovery path, or `AVAssetReader` with a `CMTimeRange` set on the output for tighter control over sample-accurate cuts. Untested here — no build/run was performed.

## Ownership and independence: the central design question

The brief asks me not to assume a parent-child design exists. It doesn't, and the retention/deletion contracts argue strongly against inventing one that *shares* files between rows:

- "Full meeting deletion removes the artifact folder even when retained audio was already deleted" (`spec/contracts/meeting-artifacts-v1.md:281-282`).
- `TranscriptionAssetCleanup.removeOwnedMeetingAudio`/`removeMeetingFolder` (`TranscriptionAssetCleanup.swift:72-83`, `246-260`) delete the *entire folder* for one transcription's `sourceFolderURL`.
- The retention sweeper detaches audio per-row by resolving that row's own folder (`MeetingAudioRetentionSweeper.swift:74-92`).

If two or more split rows pointed `meetingArtifactFolderPath`/`filePath` at the same folder or at byte-range references into the parent's `.m4a` files, deleting or "Remove Audio Only"-ing any one child would delete or truncate audio still owned by its siblings, and the retention sweeper (which fetches candidates independently per row, `MeetingAudioRetentionSweeper.swift:49-67`) would race two rows against one physical file with no locking between them. Nothing in `TranscriptionAssetCleanup` or the sweeper is folder-reference-counted; adding that would be a cross-cutting contract change well beyond a manual-split feature.

**Recommendation: each split output gets its own physically independent session folder** (a real sibling directory under `meetingRecordingsDir`, same shape as a normally recorded meeting), populated by trimming copies of the parent's source files. This:
- Requires zero changes to `MeetingArtifactStore`, `TranscriptionAssetCleanup`, `MeetingAudioRetentionSweeper`, or the recovery scanner — a split child is indistinguishable from any other meeting folder to every existing consumer. `MeetingRecordingLockFileStore.sortedSessions` only inspects folders that contain a `recording.lock` (`MeetingRecordingLockFileStore.swift:472-509`), so lock-less split folders are invisible to recovery/retention scanning and can never be misread as orphaned in-progress sessions.
- Keeps "original retained" (a settled requirement) trivial: never touch the parent's folder or row at all; only *read* from it.
- Avoids inventing folder aliasing/reference-counting rules that the recovery-retention contract does not currently support and that ADR-019/ADR-025's crash-recovery assumptions (one lock per one folder per one row) do not anticipate.

The cost is real disk duplication (below) and losing "future range provenance" for free — but the brief explicitly allows "future range provenance... but do not overengineer a generic editor," so a `sourceMeetingId` / `sourceTimeRangeMs` provenance field on the new rows (metadata only, no shared bytes) satisfies that without a shared-storage model.

## What a split must produce, per child meeting

For each of the 2–4 user-chosen ranges `[startMs, endMs)`:

1. A new `Transcription` row, `sourceType: .meeting`, fresh `id`, `createdAt` derived from the parent's start + `startMs` (so ordering/history stays coherent), `status: .completed` directly (no re-transcription required if reusing sliced text — this is the transcript brief's domain, not mine to prescribe).
2. A new folder `meetingRecordingsDir/<newSessionUUID>/` containing:
   - `meeting-playback.m4a` trimmed from the parent's `meeting-playback.m4a` (or re-mixed from trimmed raw sources — mixing is already how the canonical file is produced originally).
   - `microphone-raw.m4a` / `system-raw.m4a` trimmed from the parent's, using each source's own `startOffsetMs` to convert the shared-timeline cut point into that source's local sample offset (`MeetingSourceAlignment.Track`, `MeetingRecordingMetadata.swift:16-30`).
   - `microphone-cleaned.m4a`, if present on the parent, trimmed the same way rather than re-run through `MeetingCleanedMicRenderer` — AEC is expensive and was already computed once against the full session; re-slicing the finished artifact is strictly cheaper and avoids introducing new edge boundary artifacts from a partial AEC render.
   - `meeting-recording-metadata.json` rebuilt with new `startOffsetMs` values re-based to 0 at the child's start, `writtenFrameCount`/`timelineFrameCount` clamped to the range, and a fresh `MeetingCaptureReport` recomputed from those clamped tracks (its constructor already derives everything from `MeetingSourceAlignment` + `elapsedDurationMs`, `MeetingCaptureReport.swift:84-154`, so this is a pure function call once the trimmed tracks' frame counts are known — no need to hand-roll new report logic).
   - No `recording.lock` — the child was never "recording"; it is finalized at creation, matching how `MeetingRecordingRecoveryService.completeRecovery` treats an already-decodable finalized session (`MeetingRecordingRecoveryService.swift:624-648`).
3. `MeetingArtifactStore.materialize(transcription:promptResults:)` called once per new row to produce `manifest.json`/`meeting.md`/`transcript.json` — this is the existing, already-tested seam and needs no modification (`MeetingArtifactStore.swift:120-205`).

## Timing gaps and partial capture

If the parent meeting has recovery-inserted silence (`timelineFrameCount > writtenFrameCount`, meaning padding was inserted across a capture-recovery gap) or an `interrupted`/`coverage_shortfall` source status, a naive cut can land inside synthetic silence rather than real audio. The split UI/logic should surface the parent's `MeetingCaptureReport.sources[].status` and gap regions (derivable from `MeetingSourceAlignment.Track.timelineFrameCount` vs. real host-time continuity, though the codebase does not currently expose a list of gap *ranges*, only aggregate coverage) so a manual cut point doesn't appear to lose audio when it's actually cutting mid-padding. This is diagnostic-only; it does not block a manual, user-driven cut — the user is choosing where to cut, not the system inferring it.

A child range that spans one of these gaps should still produce a `MeetingCaptureReport` for itself using the *same* production coverage policy (`Policy.production`, 90% threshold, `MeetingCaptureReport.swift:16-35`) recomputed against the clamped elapsed/written durations for that range, so a child that happens to contain most of a coverage shortfall is honestly marked `partial` rather than inheriting the parent's overall (possibly `healthy`) verdict.

## Missing audio and old recordings

Per the audio-retention contract, saved audio can already be gone by the time a user asks to split: `filePath` cleared (retention sweep or "Remove Audio Only") while `meetingArtifactFolderPath` and non-audio artifacts remain (`spec/contracts/meeting-artifacts-v1.md:272-282`). `MeetingAudioFile.state(for:)` already models this precisely as `.saved` / `.removed` / `.missing` (`MeetingAudioFile.swift:95-109`). Splitting must gate on `MeetingAudioFile.isAvailable(for:)` first and refuse (not silently degrade) when the parent's audio is `.removed` or `.missing` — there is no audio to cut, and manufacturing a transcript-only split when the user's stated goal is separating *recordings* would be misleading. This should be a pre-flight check surfaced in the (separate) UI mockup, not something storage code guesses around.

`MeetingAudioFile.isFinalizationInProgress` (`MeetingAudioFile.swift:76-87`) — `status == .processing` or a live `recording.lock` — must also gate split eligibility: cutting from a folder that `AVFoundation` or the finalization queue may still be writing risks reading a torn/incomplete file. This mirrors the exact guard `TranscriptionAssetCleanup.detachOwnedMeetingAudio` already uses before touching audio (`TranscriptionAssetCleanup.swift:97-99`).

## Transaction / recovery lifecycle proposal

There is no existing helper for a single atomic multi-row DB transaction across the `TranscriptionRepository` (`save()` wraps one `dbQueue.write { transcription.save(db) }` per call, `TranscriptionRepository.swift:156-160`); the closest cross-row atomic precedent is `SegmentRepository.replaceSegments`, which "replaces one transcription per write transaction" (`Database/README.md:81-83`) — i.e. the codebase's established pattern is *per-row* atomicity, not multi-row batch transactions spanning several new `Transcription` inserts. A split of N children is therefore N independent row-creation units, each of which must be individually safe to fail and retry, rather than one giant transaction.

Proposed lifecycle, staged like meeting finalization (ADR-019/settlement pattern) rather than invented fresh:

1. **Plan** (pure, no I/O): validate ranges against the parent's decodable duration and audio availability; compute per-source clamped `MeetingSourceAlignment.Track`s for each child.
2. **Materialize each child's folder into a temp/staging path** (e.g. `<sessionUUID>.partial` or a dedicated staging subdirectory) before any DB write — trim audio, write `meeting-recording-metadata.json`. A failure here leaves no DB row and only orphaned staging directories, which are safe to garbage-collect on next launch (no lock file, so retention/recovery ignore them; a dedicated sweep for `*.partial`/staging leftovers would need to be added, mirroring how chunk folders are already scoped separately, `MeetingRecordingService.swift:614-615`).
3. **Rename staging → final folder** (atomic on APFS for same-volume renames) only once all files for that child are verified decodable (reusing `MeetingPlaybackArtifactBuilder`'s existing "probe before installing" discipline, `MeetingPlaybackArtifactBuilder.swift:261-283`).
4. **Insert the `Transcription` row** pointing at the now-final folder, then `MeetingArtifactStore.materialize(...)` to produce the read-view artifacts. If this step fails after folder rename but before the DB row commits, the folder is an orphan with no row — same shape as any interrupted meeting folder, safely cleanable by an explicit user-facing "clean up orphaned folders" action (not proposed here) rather than an automatic sweep, consistent with the retention contract's insistence that only explicit user actions or completed recovery/finalization delete audio (`spec/contracts/meeting-recovery-retention.md:198-200`).
5. Repeat 2–4 per child so a mid-batch failure (e.g. disk full on child 3 of 4) leaves children 1–2 as fully valid independent meetings and child 3 absent — never a half-written row or half-written folder as the persisted state. This favors partial success over all-or-nothing, which matches "original retained" and "preserve unrelated ... work" instincts better than a single wide transaction that could roll back already-good children on one late I/O error.
6. Only after all requested children are durably committed does the split flow offer to delete or archive the parent — and per "Settled," the parent's original recording is retained regardless unless the user takes a separate, explicit deletion action.

Untested: this staging/rename choreography is a proposal, not verified code; no test run was performed and none should be inferred from this report.

## Storage and performance estimate (explicit assumptions)

Assumptions: AAC `.m4a` at ~64–96 kbps mono per source (typical spoken-word bitrate observed in this pipeline's use of `kAudioFormatMPEG4AAC`, `MeetingPlaybackArtifactBuilder.swift:222`), a 60-minute parent meeting with mic+system+cleaned-mic+playback (4 audio files), split into 3 children of ~20 minutes each:

- Parent audio today: ~4 files × 60 min × ~0.7 MB/min ≈ **170 MB**.
- Each child duplicates the same 4-file set at 1/3 the duration: ~4 × 20 × 0.7 ≈ 56 MB; ×3 children ≈ **170 MB additional**, i.e. roughly **doubling** on-disk size for that meeting's audio (parent kept + full non-overlapping child set). This is the direct cost of "physically independent" over any shared/ranged design, and should be disclosed to the user (e.g. in the mockup's confirmation copy) since it's a non-trivial, unavoidable trade for the deletion-safety argument above.
- CPU/time cost: N `AVAssetExportSession`/`AVAssetReader` trims per child (up to 4 files × 4 children = 16 export operations for the extreme 4-way split), each roughly proportional to that segment's duration for AAC passthrough-range export, not full-file re-encode time — cheap relative to STT, but not instantaneous; should run off the main actor akin to existing mix/render work (`MeetingCleanedMicRenderer`, `MeetingPlaybackArtifactBuilder` are already `actor`-isolated background work).

These figures are estimates from stated assumptions, not measured; I did not build or run the app.

## Edge cases and unresolved questions

- **Legacy filename folders.** Parents using pre-rename legacy `microphone.m4a`/`system.m4a`/`meeting.m4a` (`MeetingArtifactAudioFileNames.swift:9-11`) must be read via `resolveCurrentOrLegacyURL`, but children should always be written with current filenames only ("New captures must not create legacy raw-audio filenames," `spec/contracts/meeting-artifacts-v1.md:105-106`).
- **Silent-but-valid sources.** A child range landing entirely within a diagnostic `silent` system-audio stretch (`MeetingCaptureReport.swift:38-46`, contract lines 166-182) is valid, not partial — the per-child report recomputation described above already handles this correctly since it reapplies the same policy rather than inventing new silence logic.
- **`calendarEventSnapshot`/`startContext`.** These are one-shot, whole-session facts (`MeetingRecordingMetadata.swift:70-72`). Copying them verbatim to every child is defensible provenance (they attended the same calendar event) but is a product decision, not a storage constraint — flagging for the product-facing brief/mockup rather than deciding here.
- **Prompt results / notes.** The parent's `userNotes` and any `PromptResult`s are whole-meeting artifacts with no time association; splitting cannot safely partition them. Recommendation (storage-only lens): leave both on the parent only, or copy notes verbatim to all children with no attempt to redistribute — do not invent a text-range mapping for freeform notes.
- **Does `MeetingCaptureReport`'s legacy silent-only decode-normalization interact with re-synthesized reports?** Since children get freshly *constructed* reports (not decoded old ones), the `init(from:)` legacy-promotion path (`MeetingCaptureReport.swift:167-199`) never runs for them — confirmed by reading the type, not tested at runtime.
- **Orphaned staging folders on crash mid-split.** I found no existing sweep that targets a `*.partial`/staging naming convention; one would need to be added or the choreography changed to avoid ever leaving a staged-but-uncommitted folder under the main `meetingRecordingsDir` where a naive folder-count/storage-stats view might double-count it. This is a genuine gap this investigation surfaces rather than resolves.
