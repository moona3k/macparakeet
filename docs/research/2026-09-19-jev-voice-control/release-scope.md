# Voice Control implementation and release scope

Audit date: 2026-09-19. Source audit of the active `feat/jev-voice-control` worktree during integration. This matrix compares implemented behavior with the [full feature plan](../../../plans/active/2026-09-19-jev-voice-control.md) and [routing catalog](routing-catalog.md). Later implementation changes must update the affected rows.

**Current verdict:** the branch implements the central voice-to-action architecture, native Accessibility execution, contextual recovery and local task observability. It does not yet implement every route in the full feature plan, and it is not a qualified stable release. A PR can accurately deliver a substantial explicitly enabled developer beta with synthetic native fixture evidence. Native Google Flights success has not been demonstrated. Describing it as the completed full feature or a ready stable release would overstate the current source and evidence.

## Distribution and agent access

`AppFeatures.voiceControlEnabled` is **false**. `--enable-voice-control` works only in DEBUG builds. Stable builds therefore do not expose this feature through that argument. This is a deliberate gate, not a full public launch.

Browser control uses native macOS Accessibility, with no extension, native-host
registration, CDP, dedicated browser profile or browser restart. The earlier
extension implementation is preserved as uncompiled historical research. Its
recording is not evidence for the native path. Native browser qualification must
state the actual browser, website/fixture, supported controls and observed limits.

There is **no new public `macparakeet-cli` Voice Control command**. Existing library/Transform CLI commands do not expose the new live control runner. The app's typed instruction field and the internal qualification harness are not agent-native CLI parity. The plan explicitly calls CLI a future possible surface, so it is not a prerequisite for the present developer beta; adding it later requires a defined app-IPC/consent boundary, CLI changelog, integration documentation and contract tests. The retired native-messaging experiment is not shipped.

## What the demonstrations establish

A historical headless Chrome extension/native-host/socket/live-Jev run against a synthetic flight form proved that **retired** transport’s dynamic control loop. It is not native-path, confirmation-UX, microphone, or real-site evidence. See [historical-browser-extension](historical-browser-extension/README.md).

A native AX/live-Jev two-field synthetic goal succeeded separately. It does not establish Mail/Safari/Finder compatibility. Any later recorded-speech trial should state whether audio came from a physical microphone, a prerecorded file, or synthetic speech; those are different evidence classes. See [evidence](evidence.md).

## Remaining work for a coherent PR and full release

Desktop qualification is being performed separately. Independent code, documentation, review and PR preparation can proceed while it runs; a PR must not imply that pending qualification has passed. No native Google Flights completion or production demo recording is established here.

For a coherent PR, keep the feature gated; make the title, description and walkthrough match the implemented rows above; include exact final regression results and runtime artifacts; resolve outstanding safety findings; provide reproducible developer setup and known compatibility limits. Update the plan's proposal-only status to reflect actual implementation without marking unfinished routes complete. The existing HTML walkthrough presents proposed scope and must clearly distinguish it from current availability.

For the user's requested full feature, the unavailable capability rows remain real implementation work: broader referent grammar/numbered choices, richer precise editing/spelling and inverses, explicit sequences, supported window/tab/system/domain operations, content-reading/cross-app workflows, and richer target feedback. OCR/grid is explicitly optional in the plan and should be separately scoped, not silently claimed.

For stable distribution, finish native browser qualification, named native/browser/speech-engine compatibility trials, representative end-to-end latency/correctness evaluation, physical interruption/confirmation/accessibility qualification, regression checks for existing capture modes, and normal signed/notarized release verification. A successful fixture video or passing focused suite does not replace these gates.
